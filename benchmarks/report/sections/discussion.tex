\section{Discussion}
\label{sec:discussion}

\paragraph{Incidence and intersection.} An incidence lookup in HStore reads one entry of the reverse index. For most atoms the whole incidence set is stored inline in that entry, and for hubs it is the root of a small tree. The visitor API hands each hyperedge id to the caller without allocating, which is why \wl{read.incidence} allocates about one byte per lookup. HyperGraphDB opens a JE cursor on a duplicate set, decodes 16-byte handles, and builds a result object per lookup. With a 64\,MiB JE cache, part of each lookup also misses the cache and reads from the log files (\cref{app:full}). Co-membership adds a second effect. HStore intersects two sorted incidence trees and skips every subtree whose key range cannot match, so the cost follows the smaller set. HyperGraphDB plans \texttt{hg.and} as a general conjunctive query over two result sets. The two-hop workload combines both lookups, so it inherits both advantages.

\paragraph{Member enumeration, and where HyperGraphDB leads.} HyperGraphDB keeps a link's targets as a Java array in its atom cache, so enumerating the members of a cached link is an array loop with almost no allocation. HStore reads a hyperedge's members from its record in the catalog tree: from the leaf stored inline in the record for a small edge, or from the edge's own membership tree. At scale 1 the catalog fits in HStore's node cache, and HStore is faster at the median, though the run ranges overlap. At scale 4 it does not. Member lookups then miss the cache and decode catalog pages again, which costs \M{allocChstorereadmembers} of allocation per lookup on average, while HyperGraphDB's atom cache, which the 64\,MiB budget does not limit, still holds the links. This is the clearest weakness this study found in HStore. Two directions would address it: smaller catalog pages, or a cache of decoded edge records separate from the node cache. Both trade memory for this access pattern, and neither is in the version measured here.

\paragraph{Small writes.} A single-update commit in HStore appends a log record of a few hundred bytes and publishes new roots in memory. The tree pages are written later, by a checkpoint that writes each changed node once for all the commits since the previous one. A JE commit appends to its log a new version of each changed record and of the B+tree internal nodes above it, in every JE database the change touches. The difference shows directly in bytes written per update (\cref{fig:writes}). Under asynchronous commits, the per-commit cost that remains in HStore is the commit itself: copying the changed tree paths in memory and publishing a generation. That cost is close to JE's at the median, and the gap opens in the tail.

\paragraph{Tail latency.} HStore readers pin an immutable generation and never wait for a writer, a checkpoint or a compaction. Writers wait only for the commit lock, which a checkpoint takes just to swap stored references into the head. HyperGraphDB reads run inside JE transactions, which take record locks, and JE's cleaner and checkpointer compete for the same latches and log. In 15 of the 18 latency measurements (six workloads in three configurations), the gap between the two systems is wider at p99 and p99.9 than at the median. The three exceptions are the \wl{mixed} writer under synchronous commits, where HyperGraphDB fell behind its schedule and the gap is largest at the median, and single-update commits and the \wl{mixed} writer at scale 4, where HStore's advantage stays between 1.3 and 2.5 times across percentiles. The single slowest commit at scale 4 was HStore's.

\paragraph{Giant hyperedges.} HStore bulk-builds a large membership tree bottom-up in one pass, and a membership probe is one descent of that tree. HyperGraphDB stores the giant link as one record holding 50,000 handles (200,000 at scale 4). A membership probe goes through the node's incidence set instead.

\paragraph{Footprint and reclamation.} Several layout choices keep HStore's files small: 8-byte ids stored as varint gaps instead of 16-byte handles, node images packed into 64-byte units, and small member trees and incidence sets stored inline in their parent record. HStore's log is also truncated at each checkpoint. A JE log keeps every superseded version until the cleaner copies the live entries out of a file and deletes it, and at scale 4 cleaning dominated HyperGraphDB's bytes written. HStore's weak point is the period right after a large delete. Pages replaced by the deletes stay on disk while any of the 64 retained generations can reach them, so the files grow first and shrink only after the history moves on, here at the restart that follows. An application that deletes heavily and needs its disk space back quickly would set a smaller \texttt{history\_limit}.

\paragraph{Opening and recovery.} After a clean shutdown, HStore reads one catalog image and finds nothing in the log to replay. HyperGraphDB's open takes longer and allocates far more heap: \M{allocAhgdbreopen} per reopen at scale 1, against \M{allocAhstorereopen} for HStore. After a crash, HStore replays the logged key changes of every commit since its last checkpoint, and JE replays its log from its last checkpoint. HStore's replay cost grows with the number of commits since the last checkpoint, which the write buffer and the checkpoint thresholds bound. The recovery times of the two systems overlap in our runs, so we do not claim a difference.

\paragraph{What HStore spends.} HStore retains more heap after ingest than HyperGraphDB (\cref{tab:memory}). The retained heap includes nodes not yet written by a checkpoint, up to the 64\,MiB write buffer, and the node cache, whose 64\,MiB budget is an estimate that runs below the true heap size. HStore also allocates slightly more per inserted node at scale 1 and pays more GC time during ingest there, and more GC time during the deletes at scale 4. Its worst single commit at scale 4 was slower than HyperGraphDB's, even though its p99 and p99.9 were lower.
